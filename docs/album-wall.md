## 1. 它是什么

**一整块可以拖着走的照片海**，波浪 Banner 是它的「幕布」。

- **滚轮往下 = 掀开幕布**：波浪整块升起，照片海整屏接管。滚轮**只管滚页面**，从不接管画布
- **左键拖动 = 二维平移**：上下左右都能拖，滑到边界有橡皮筋，松手弹回
- **画布比屏幕宽好几倍**：一屏只看得到五六列，横向还有得拖（列数自动配平，见 §3.2）
- **点一下原地放大**：那张照片变成「**比例菜单里某一档的放大版**」，占整数列 × 整数行，
  四周只剩一个标准间隙；其余照片顺着让开，压暗，相机把它推到视口正中（避开顶部导航）
- **再点一下进灯箱**：滚轮以光标为中心缩放、拖动查看、左右切换
- **左侧竖向分类栏（毛玻璃抽屉）**：贴住整屏左边缘、上下居中；收起 / 展开的把手长在玻璃**侧面**
  （右侧一根长条，只有一个箭头，没有文字）。毛玻璃的颜色来自它盖住的那几张照片
  （`backdrop-filter` 采样真实像素 + 模糊 + 提饱和），浅色照片上是白雾、深色照片上是墨色。
  切换分类时整片重新排列
- **右下角一个圆形图标 = 回到正中**（和分类抽屉同一块玻璃，不占抽屉的位置）
- **画布外面不是死黑**：星尘 + 星云 + 画布边缘的微光，拖到头会觉得「海还在继续，只是过不去」

缩略图一律裁成**九档规整比例**之一（9:16 / 2:3 / 3:4 / 1:1 / 4:3 / 3:2 / 16:9 / 2:1 / 3:1），
高度都是整数像素（列宽 216 时 = 384 / 324 / 288 / 216 / 162 / 144 / 122 / 108 / 72），
于是「不重叠 / 不留缝 / 上下两条边齐」是**构造上成立**的，不是调参调出来的（见 §3）。
列宽 216（缺省）= 1440 屏一屏约 6.4 列，是「整体大小」唯一的旋钮（§3.2）。

排序是**确定的**：`photos[]` 的数组顺序 = 照片海从左到右、从上到下流动的顺序。
刷新、分享链接、筛选后重排，位置都能复现 —— 这是「可 deep-link 到某张图」和「用户知道自己看完了」的前提。

## 2. 交互状态机

```
   ╔══════════════════════════════════════════════════════╗
   ║  curtain  滚轮往下，波浪升起，照片海整屏接管（可逆） ║
   ╚══════════════════════════════════════════════════════╝
                              │
                              ▼
   ┌────────┐  点照片   ┌─────────┐  点同一张  ┌────────┐
   │  idle  │ ────────▶ │  focus  │ ─────────▶ │  zoom  │
   └────────┘           └─────────┘            └────────┘
        ▲                     │                      │
        └────── Esc / 点空白 ──┴────── Esc / 点遮罩 ───┘
                              ▲  点别的照片
                              └──────────────────────
```

| 状态 | 表现 |
|---|---|
| `curtain` | 首屏就是整块 Banner（`100svh`）。往下滚它就自然被顶出视口，滚回来它自然落回来；滚到底就是 `idle` |
| `idle` | 照片海铺满整屏，相机停在画布正中，可任意方向拖 |
| `focus` | 点中那张**原地**放大成「比例档的放大版」「整数列 × 整数行」，**横向铺满它占的那 k 列**（1440×900 下：9:16 440×782、1:1 664×664、16:9 888×500…）、其余照片被障碍感知的打包器重排让开、整体压暗（`filter: brightness`）、相机把它推到**可用区**正中（避开顶部导航胶囊，横向纵向都居中），底边浮出标题条 |
| `zoom` | 灯箱：黑底、`contain` 显示、滚轮以光标为中心缩放（1×–6×）、**手机双指缩放 / 双指平移**、放大后可单指（鼠标）拖动、双击在 1× 与 2.4× 之间切换、← → 切照片、Esc 逐级退回 |

### 手势与快捷键

| 操作 | 桌面（相机模式） | 手机（滚动模式） |
|---|---|---|
| 进出照片墙 | 滚轮上下（掀 / 落幕布） | 页面正常滚动 |
| 平移 | 按住左键拖（二维，带橡皮筋） | 页面正常滚动 |
| 滚轮 | **只滚页面**；到顶到底之后就没有别的了 | 页面正常滚动 |
| 点照片 | 放大 | 放大（并自动滚到视口中央） |
| 点放大的那张 | 进灯箱 | 进灯箱 |
| 拖动放大的那张 | 平移整片海（照片不会被拖走） | — |
| **灯箱里双指张开 / 捏合** | —（鼠标走滚轮 / 双击） | **缩放 1×–6×，以两指中点为锚**；两指一起挪 = 平移 |
| 灯箱里单指拖（放大后） | 鼠标拖动查看 | 同上（一指即可） |
| 灯箱里的 ± / ⤢ 按钮 | 手动 1.5× 步进 / 回到原始大小 | 同左（双指不方便时用） |
| 点空白 | 不退出（避免误触）；`Esc` 才退出 | 同左 |
| `Esc` | 灯箱 → 放大 → 常态，逐级退 | 同左 |
| `← →` | 灯箱里换照片 | 同左 |

右下角那个圆形图标 **「回到正中」是两段式**：

1. **有放大照、但镜头没把它摆在正中** → 只做这件事：把放大照送回可用区正中（不退出放大）。
   拖开画面看过之后，点它就是「回到那张照片」。
2. **再点一下**（或本来就没有放大照）→ 退出放大，相机**精确回到初始位**（= 载入时那片海的正中，
   和第一次进页面时逐字节相同）。

判断「有没有居中」不靠状态位，而是比相机与目标的距离（> 2px 才算没居中），
所以中途拖过画面就自动回到第一段。按钮的 `title` / `aria-label` 会跟着三段状态改
（「把放大照移到正中」/「退出放大，回到初始视角」/「回到照片海正中」）。

## 3. 排版算法

### 3.1 格点打包（`packGrid`）

固定列宽、列对齐、行不对齐（瀑布流）。**不是**简单的「记每列高度」，而是每列维护一份「已占用区间」：

```ts
type Span = [start, end];            // 同一列内按 start 升序

firstFit(col, h, from) → y           // 找第一个 ≥ from 且放得下 h 的位置（障碍感知）
occupy(col, y, h)                    // 往区间表里插一段
```

每张照片挑「`firstFit` 返回最小 y」的那一列（同样早就选靠左的）。

**为什么不用「每列高度」**：放大照要按列占掉一条矩形（`Barrier`），
被它压住的列如果只记「当前高度」，就没法把障碍上方和下方分开算。

**高度从哪来（v3 的核心）**：每张照片先按原比例吸附到比例菜单里的一档 `cell.snapped`，
`cell.menuH = round(colW / snapped)` —— 永远是整数（列宽 216 时就是 384…72 那九档）。
初排、放大、退出放大、筛选、窗口缩放**全走这一个函数**，区别只是有没有障碍矩形。
打包完再跑 `normalizeBottom()` 把各列底边拉到同一条线（见 3.3 ⑤），
于是照片海是一个上边和下边都齐的矩形。

### 3.2 列数与画布宽度

```
colW    = clamp(snapTo(columnWidth * clamp(vw/1440, 0.72, 1.16), 72), 144, 432)
列数     = round((3.2 * vw + gap) / (colW + gap))             // 横向最多铺 3.2 屏宽（常量 BOARD_SCREENS）
列数     = min(列数, ceil(Σ(colW / snapped) / (vh * 1.45)))   // 但竖向至少能拖得动 1.45 屏
画布宽   = 列数 * colW + (列数 - 1) * gap
```

**`columnWidth` 就是「整体大小」唯一该动的旋钮**：照片、间隙之外的间距、放大照的宽度
全部由 `colW` 派生，改它一个值，排版规则、动画、不变量一条都不用改。

`colW` 吸附到 **72 的倍数**是硬约束，不是审美：格点步长 = `gcd(九档高度 + 缝, 缝)`，
只有 72 的倍数才让这个 gcd 保持 **2px**（216 → 392/332/296/224/170/152/130/116/80，gcd = 2），
于是「所有格子的上下沿都落在 2px 格点上」成立，放大照吸附之后**残差恒为 0**。
可选值：144 / 216 / 288 / 360 / 432（144 = 1440 屏 9.9 列很密；288 = 4.9 列，照片明显更大）。

> 曾经写「必须 144 的倍数，九档高度才是整数」：其实菜单高度一律经过 `round()`，
> 任何列宽都是整数；真正需要整除关系的是**格点步长**，72 的倍数就够，于是多了 216 这一档。
> 缺省值从 288 调到 216（2026-11 用户反馈「整体有点偏大」），一屏 4.9 列 → 6.4 列。

第二条很关键：照片少的时候，光按宽度算会得到「又宽又扁」的一条，
竖向根本拖不动 —— 宁可变窄也要让上下有事可做。**只统计当前可见的照片**，
所以筛完只剩 30 张时它会自动收回成四五列，而不是摊成一条横幅。

> 因为这条「竖向至少 1.45 屏」的规则更强势，**横向那个上限（3.2 屏）大多数时候根本不起作用**：
> 160 张时它和竖向规则刚好打平（都是 21 列），30 张时列数完全由竖向规则定死。
> 所以原来的配置项 `boardWidth` 已被删成一个常量 —— 留个滑块只会让人以为调它有变化。

#### 可调项只剩 5 个

| 项 | 范围 | 为什么留 |
|---|---|---|
| `columnWidth` 列宽 | 144–432（72 的倍数） | 「整体大小」唯一该动的旋钮（本节） |
| `gap` 间隙 | 0–24 | 纯外观。实测 0 / 9 / 24 三档排版全绿（奇数缝的格点步长退到 1px，残差仍 ≤ 1px） |
| `radius` 圆角 | 0–18 | 纯 CSS，碰不到排版 |
| `focusWidth` 放大宽度 | 0.50–0.90 | 放大照的宽度上限（高度另有硬约束，见 §3.3 ②） |
| `dim` 变暗 | 0–0.90 | 纯 CSS，碰不到排版 |

删掉的两项（2026-11，用户：「不是必须的或者会破坏排版的都可以删」）：

* `boardWidth`（画布几屏宽）→ 改成常量 `BOARD_SCREENS = 3.2`：见上面的引用块，基本是死旋钮。
* `focusMaxHeight`（放大照高度上限）→ 高度天花板改成**可用区**本身。这个滑块调小只会让放大照
  提前被裁；调到 0.5 时 `①高度优先` 会直接找不到 2 列的档，退回「整块顶出屏幕」的老毛病 ——
  也就是说它**能破坏刚刚修好的「不出屏幕」**。`focusWidth` 的下限也从 0.3 提到 0.5
  （0.3 时 1440 屏的 2 列宽 440 > 盒 432，横图会退成 1 列 = 和缩略图一样大 = 点了没反应）。

### 3.3 放大（`packFocus()`）—— 一个障碍矩形 + 「能不动就不动」的让位

目标：照片**在原地**长大（不会飞走），**四条边都落在网格上**，四周只剩一个标准间隙，
并且照片海的上边、下边都是直线。

```ts
private packFocus(): void {
  packGrid(null, null, 0);                                  // ① 基准版面（= 静止时的样子）
  let info = heroLayout(hero, idle, idleLine);                // ② 算放大照的矩形
  packGrid(info.barrier, hero, info.rect.y + info.rect.h);    // ③ 以它为障碍把其余照片重排
  info = pinBandBottom(hero, idle, idleLine, info);           // ③′ 下沿钉在板底线上（不然下方有凹口）
  info = flushBandTop(hero, idle, idleLine, info, pinned);    // ③″ 上沿拉直（末张拉长/裁短到接住）
  hero.rect = info.rect;                                      // ④ 放大照上位（它不参于打包）
}
```

> 上一版那一整套 `openBand` / `bandFitsDown` / `bandFitsUp` / `cover` / `nudge` / `MIN_KEEP`
> 全部删掉了：**格点化之后，"谁来让位、让多少"变成打包器的自然结果**，不再需要可行性推演。

#### ① 基准版面

先跑一遍无障碍的 `packGrid`，拿到的就是静止时的版面。放大照的「原地位置」从这里读，
所以它永远在自己原来那一格附近长大，不会飞走。

#### ② `heroLayout()`：放大照的矩形

```
ratio   = hero.snapped（2:1 / 3:1 的全景按 16:9 显示，否则放大后是一条看不清的扁横条）
BOX_W   = focusWidth × vw               // 0.68，宽度上限
BAND_H  = snapTo(vh − 导航高度)          // 可用区：放大照**必须整个装得进这一块**（也是高度上限）

① 高度优先：在「宽 ≤ BOX_W 且 高 = 宽 ÷ ratio ≤ BAND_H」的整数列里取**最宽**的一档
② 一档都装不下（矮窗口 + 竖图）：允许最宽高出 HERO_OVERFLOW(1.35) 倍的那个 k，
   但把盒子**裁到 BAND_H**（照片上少看一截，不是整块顶出屏幕）
竖图兜底：k 至少 2（1 列 = 和缩略图一样大，等于点了没反应）
高 = snapTo(裁切后的宽 ÷ ratio, 格点步长)
x  = col·pitch                          // 铺满 col … col+k−1 这 k 列
top = 先按「原地 y」吸到格点，再由 ③′ / ③″ 微调（下沿钉底线、上沿对齐邻居）
```

**放大照只占整列，横向一定铺满它那 k 列 —— 左右不留一条空档。**
这是硬性的：照片墙上每张图（含放大那张）都严格按整列扑上去。

> ⚠ 初版 v3 曾用「边界列变窄」把宽度精确到 1px（能把 9:16 做到 458 宽、正好卡在
> 当时的高度上限上），代价是放大照两侧各留一条空档 —— 9:16 左右各 60px、
> 4:3 各 43px，看上去就是网格破了个洞。**已废弃**：宁可把盒子裁矮一点（②），
> 也不让网格出现空缺。

实测放大照尺寸（1440×900、列宽 216、`focusWidth 0.68`、可用高 814）：

| 比例档 | 放大照 | 列数 | 占屏 | 比可用区高出 |
|---|---|---|---|---|
| 9:16 | 440×782 | 2 | 31%×87% | 0（装得下） |
| 2:3 | 440×660 | 2 | 31%×73% | 0 |
| 3:4 | 440×586 | 2 | 31%×65% | 0 |
| 1:1 | 664×664 | 3 | 46%×74% | 0 |
| 4:3 | 888×666 | 4 | 62%×74% | 0 |
| 3:2 | 888×592 | 4 | 62%×66% | 0 |
| 16:9 | 888×500 | 4 | 62%×56% | 0 |

**一屏之内永远装得下**（1440×900 / 1600×1000 / 1680×1050 / 1920×1080 实测 `overflow ≤ 0`），
相机把它推到可用区正中（横纵偏差 ≤ 1px）。

> 窗口矮到「2 列竖图都比可用区高」时（1440×780、1280×720 实测）：盒子裁到可用区高度，
> 比如 9:16 从 782 裁到 694 / 634 —— 照片上看不到最上最下那一点，点第二次进灯箱看全图。
> 这是「不出屏幕」与「整列铺满」两条硬约束下唯一的做法：不裁就只剩「退回 1 列 = 点了没反应」。

> **为什么不能靠收窄宽度来降高度**：收窄就会在放大照两侧留一条 `colW − 实际宽` 的空档，
> 那正是用户反复报的「空白」。

> 比可用区还高的极端情况（窗口高度 < ~600 且是竖图）仍会退回「2 列、原样高出屏幕」，
> 靠拖动查看 —— 此时 `.gal-cell.is-tall` 会把标题条改挂到照片顶上。

#### ③ `packGrid(barrier)`：**能不动就不动**

静止版面先拍一份快照（`cell.idle`）。放大时每张照片先试着待在**它自己原来那一格**：

* 原位没被放大照占到 → 连 `transform` 都不写（这占绝大多数，十几列完全静止）
* 原位被占到 → 它让开，等其它照片都站好之后，落到**板子下沿那一排**（唯一没人的地方）

被顶走的照片会在自己那一列留下空洞，所以带那几列还要按原顺序**重贴一遍**（跳过放大照），
观感是「这一列顺着放大照滑上去」，不会破一个洞。

> 为什么不把它们就近插进旁边的列：插一张进去，那一列从插入点往下的**所有**照片都要下沉，
> 连锁反应比直接让它们走一趟还乱（实测 movers 从 30 涨到 100+，板子还高 500px）。

实测（1440×900、列宽 216、160 张、随机抽 20 张点开）：**平均每张只有 14.4 张照片移动**
（其中 ~6 张是「必须走远」的），**没有人换列**的情况占多数，位移中位数 120–640px。
列宽 288 时是 29 张 / 9 张，改造前是 155 张全动、145 张换列、中位数 1200px ——
放大照整体变小之后，需要让开的人也少了。

#### ③′ `pinBandBottom()`：下沿钉在板底线上

放大照那 k 列下面要是没有照片了（点的是最后几排时必然如此），
它们的「视觉下沿」就是放大照的下沿 —— 那就必须等于整片海的底线，
否则放大照下方空出一条**凹口**（用户报的「空白」）。

```
若某带列下面已无照片（bandOpenBelow）：
    want = snapTo(底线 − heroH)      // 上下两个方向都试，不只是往下推
    重排 → 底线自己也会动 → 再算一遍     // 不动点迭代，六轮足够（误差按 1/3 收敛）
```

以前只会「往下推」且只推四轮，推过头就再也回不来；而且后来上沿一动，
下面那条凹口又会冒出来 —— 所以 ③″ 必须**知道下沿是不是钉死的**。

#### ③″ `flushBandTop()`：上沿也要是直线

放大照是个直角矩形，它上方那 k 列的照片必须**一条线**停在「上沿 − gap」。
但瀑布流各列末张天然错开几十上百像素，不处理就会在某一列上方留一条空档
（实测 100–170px，且**随窗口尺寸变化**——哪几张落在哪列一变，缺口就换位置）。

处理办法：把每列「带上方最后一张」拉长 / 裁短到刚好接住。

```
· 拉长上限 2.5 × 菜单高度、裁短下限 ≈ 55%（TAIL_SHRINK / TAIL_MIN）
  —— 缩略图是 object-fit: cover 的取景框，改高度只是换取景，不会变形
· 上沿本身也可以挪：候选 = 每个末张的「自然接住位置」+ 最低 / 最高 / 中位
  选「被改得最狠的那一张也改得最少」的那个（minimax）
· 但下沿已经钉在底线上时（③′）上沿**不许动**，只把末张调整到位
```

> 这条和 `normalizeBottom()` 一样，属于「每列允许有一格破例」：
> 末格（拉到底线）和带上方末张（接住放大照的直角）。两种破例都不参与打包，
> 所以不会引起连锁反应。三条边（上沿 / 下沿 / 底线）都对齐之后，
> 放大照四周**只剩一个标准间隙**，任何窗口尺寸下都是如此。

#### ⑤ `normalizeBottom()`：底线对齐

每列只动**最后一格**：

```
line = 各列末格下沿的共同位置（在 [最矮能缩到, 最高能拉到] 之间按 minimax 选，
       让「被改得最狠的那一列」改得最少）
末格.h = line − 末格.y      // 下界 MIN_LAST(96) / 上界 2.5 × 菜单高度
```

* 只动一格、列内独立 → 不可能制造空洞，也不可能影响别的列；
* **钉死**：放大照那几列如果下面已经没照片了，它们的「视觉下沿」就是放大照的下沿，
  `line` 直接取那个值（否则放大照下方会空出一块）；取不到时由 ③′ 把放大照挪到线上；
* 拉不起来（列太短）就放宽到 `2.5 × 菜单高度`（换成更宽的取景框），仍不够才抬 `line`。

#### ④ 相机：居中在「可用区」里

`centerOnFocus()` 把放大照居中，但**避开顶部固定导航**：
可用区 = `[导航底边, 视口底边]`，`heroH` 的上限也按这个可用区算。
否则竖图放大后上沿会被玻璃胶囊压住二三十像素 —— 排版其实是对的，看起来却像没对齐
（`safeTop` 用 `offsetTop + offsetHeight` 量，不用 `getBoundingClientRect`：
导航滚动时会 `translateY(-120%)` 收起来，rect 会变负，照片就会跟着跳）。

这段计算抽成了 `focusCamTarget()`（只算不动），因为右下角那个「回到正中」要靠它判断
「现在到底居中了没有」：`centerOnFocus()` 和 `resetCam()` 都用同一个函数，
两条路径的居中位置在构造上一致（实测偏差 0px）。

相机和重排**同时**开始（同一个 `--gal-dur`、同一条缓动曲线），
放大照在长、邻居在让、镜头在滑，叠成一段连续位移。

> 用户明确允许「所有照片的缩略图比例都可以变，只要最上最下的边框行对齐就行」——
> 现在的规则更硬：**缩略图永远在九档菜单里，只有每列末格和带上沿那一格破例**。
> `paint()` 里高度写的是 `rect.h / scale`（缩放前的盒子高），缩放之后正好等于排版高度，
> 比例对不上时 `object-fit: cover` 自动裁切，照片不会变形。

### 3.4 位置怎么落到 DOM

**每个元素只在列宽变化时设一次尺寸**（`colW × colW/aspect`），此后一切都是 `transform`：

```css
transform: translate3d(x, y, 0) scale(rect.w / baseW);
```

照片宽高比固定，所以「等比缩放 + 平移」就能表达任意排版结果。
筛选 / 放大 / 窗口缩放全在合成层上动，**不进 layout、不重绘** —— 160 张图一起变形也能 60fps。

## 4. 相机模型

```ts
cam = { x, y }   // 视口左上角落在画布坐标系的哪一点
stage.style.transform = `translate3d(${-cam.x}px, ${-cam.y}px, 0)`;
```

- **只有左键拖动会动相机**（`pointerdown/move/up` + 位移超过 `DRAG_START` 才算拖）
- **滚轮完全不接管**：没有 `wheel` 监听，滚轮只走页面滚动（也就是掀 / 落幕布）
- **弹性边界**：越界用 `RUBBER = 0.34` 压住，松手 560ms 弹回
- **小画布自动居中**：画布比视口窄时（筛完只剩几张），相机锁在正中间，不贴左上角
- **放大的照片尽量居中，但优先「照片海填满屏幕」**：`camBounds(false)` 是**程序化居中**用的，
  只允许露出画布边框外 6% 那么一点点，然后 `centerOnFocus()` 再保证放大照本身整张看得见。
  于是贴边的照片不会被推到「半屏都是空白/星尘」的位置 —— 它会在靠近那条边的地方停下
  （实测：中间的照片居中误差 0~2px；贴底那张放大照整张可见，屏幕下沿正好是照片海的下边缘）。
  拖动 / 回弹仍然用 `camBounds(true)`（把「让放大照居中」的那个 cam 值并进区间），
  所以你想看边框外面照样拖得出去

> ⚠ 视口容器必须写 `overflow: clip` 而不是 `overflow: hidden`：
> `hidden` 的容器**仍然是可编程滚动的**，浏览器「把元素滚进视口」之类的逻辑会把它悄悄滚走，
> 整块画布随之错位。

### 4.1 幕布（进入方式）

**幕布是普通滚动内容，不是被 JS 搬上去的**：

```
main
├── .gal-curtain  波浪 Banner，position: relative（100svh 高，z-index 10）
├── .gal          position: fixed; height: 100svh（z-index 自动，在幕布后面）
│   ├── .gal-stars     星尘 canvas
│   ├── .gal-view      视口
│   ├── .gal-rail      毛玻璃分类抽屉 + 侧面的把手（opacity: var(--gal-enter)）
│   └── .gal-reset     右下角圆形「回到正中」
└── .gal-spacer   height: 一屏                     ← 再补一屏，页面正好能滚过 banner
```

- 往下滚：幕布被自然顶出视口，照片海（fixed）纹丝不动 —— 视差感来自「一个动一个不动」
- 往回滚：幕布自然落回来，**永远回得到最上面那张 Banner**
- 滚到底就没有更多可滚的了，于是「滚轮只负责页面」这句话在墙内天然成立，
  不需要任何 preventDefault，也不会和触控板/惯性脚本打架
- 分类抽屉和提示的透明度跟着 `--gal-enter` 走（脚本只写这个变量）：幕布没升起之前它们不出现

> ⚠ 上面这一整套（`100svh` 的幕布 + 补一屏的 spacer + `--gal-enter`）**只在相机模式成立**，
> 也就是「桌面 + 鼠标」。CSS 里那条把 `.banner` 撑成整屏的规则包在
> `@media (min-width: 900px) and (pointer: fine)` 里 —— 它和 `SCROLL_QUERY` 互补，
> 脚本一换成滚动模式，Banner 就自动退回**全站统一的首图**（宽高跟图片比例走、
> 移动端封顶 40svh，和别的页面像素级一致），照片海接着往下排。
> 别把那条规则放回无条件生效的位置：手机上 Banner 会变成一整屏，看着像「换了个站」。

> ⚠ 别再回去用「scroll 事件里写 `translateY(-scrollY)`」那套。scroll 回调里读到的
> `window.scrollY` 常常是**上一帧**的值（平滑滚动、滚动锚定、程序化 scrollTo 都会），
> 幕布就会一直慢一拍 —— 滚到一半往回滚时照片海和底色直接错位，露一大片空白。
>
> ⚠ `.gal` 的高度必须显式写 `height: 100svh`。只写 `inset: 0` 时，某些时刻（祖先临时
> 变成了 fixed 的包含块）它会跟着 main 一起长高（1800 → 2700 → 3600，每次 +一屏），
> `vh` 被带偏 → 列数一路缩水 → 整片墙的照片都挪位。同理，`vh` 只信 `window.innerHeight`，
> 绝不读 `.gal` 的 `clientHeight`。

### 4.2 为什么变暗不用「一层半透明黑」

`.gal-stage` 有 `will-change: transform`（自成层叠上下文），放大那张就算 `z-index` 再高，
也翻不过盖在画布外面的那层黑 —— 整张照片会被一起压暗。所以：

1. `.gal-dim` 只沉在画布**下面**（z-index 0），压星尘和底色；
2. 其余照片各自 `filter: brightness(calc(1 - dim × 0.72)) saturate(.92)`，走合成层。

## 5. 星尘 / 星云（`Dust`）

画布外面那圈不能是死黑，否则「拖到边」就像撞墙。

- 一层**预渲染**的星云（4 个软径向色团，`buildGlow()` 只在 resize / 换主题时重画）
- 一层**浮尘**：`clamp(vw×vh/11000, 50, 180)` 颗，约 14% 是「大颗浮尘」
- 每颗有自己的**视差深度** `d ∈ [0.03, 0.36]`：相机往右走，星尘往左漂一点点，于是有纵深
- 闪烁用 `sin`，`prefers-reduced-motion` 下静止；`document.hidden` 时跳过绘制
- 颜色从主题里**探**一次（隐形探针 `color: oklch(var(--bc))` / `background-color: oklch(var(--p))`），
  深浅主题自动对上；换主题时 `MutationObserver` 监听 `data-theme` 重新探色

## 6. 数据模型

`config/gallery.json`：

```jsonc
{
  "_说明": "给人看的备注，保存时原样保留",
  "settings": {
    "columnWidth": 216,     // 一列的基准宽度（px）= 整体大小。必须取 72 的倍数：144 / 216 / 288 / 360 / 432
    "gap": 8,               // 图与图的间隙（px）—— 放大时四周用的也是它
    "radius": 4,            // 图片圆角（px）
    "focusWidth": 0.68,     // 放大那张的最大宽度（占视口宽度；实际会吸附到整列且优先保证装得下）
    "dim": 0.6              // 其余照片压暗多少
  },
  "railTags": ["旅行"],      // 可选：左侧分类栏只展示这些标签（空 / 缺省 = 全部；顺序即栏内顺序）
  "photos": [
    {
      "id": "g0001",                    // 稳定 id（筛选 / 放大 / ?p= 都用它）
      "src": "/image/gallery/g-01.svg", // 图床 URL / 仓库路径 / 外链，三种都认
      "w": 1200, "h": 900,              // 像素尺寸（排版按它算宽高比）
      "title": "海边",                   // 可选：放大时底部标题条 + 灯箱标题
      "description": "",                // 可选
      "tags": ["旅行", "风景"],          // 可选：分类标签，可多个
      "date": "2026-05-20"              // 可选：灯箱底部信息
    }
  ]
}
```

要点：

- **扁平**：没有「相册」这一层。一张图属于什么分类，完全由 `tags` 决定，
  所以同一张图可以既在「旅行」又在「夜景」里。
- **真实尺寸**：记 `w/h`，宽高比被夹在 0.28–4（超长截图不会把一整列撑爆）。
- **顺序即排版**：数组顺序就是流动顺序，管理面板拖缩略图改的就是它。
- **展示分类（`railTags`）**：左侧分类栏列哪些标签，由这个白名单决定 ——
  `["旅行"]` 就是「哪怕有旅行、黄山两种图，左边也只列旅行」。
  空 / 缺省 = 全部展示（以后新加的标签也会自动出现）；非空时**顺序就是栏内顺序**。
  它只管「栏里列哪些」，不管照片归属：被藏起来的标签，照片照样在「全部」里，
  深链 `?tag=黄山` 也照样能筛；想让照片也不出现，就把标签从照片上摘掉。
  管理面板会顺手剪掉已经没有任何照片的孤儿名字。
- 改完要重启 dev 或重新 build（构建期 `import` 这份 JSON）。
- **仓库里的 `photos` 是空的**：演示用的占位图（`public/image/gallery/`，160 张 SVG）
  已被 `.gitignore` 排除。想本地看演示效果就跑一次 `npm run gen:assets`
  （`scripts/gen-placeholders.mjs`）生成占位图，再自己往 `config/gallery.json` 里加数据；
  真实照片走图床，`/config → 照片墙` 里批量上传就行。

## 8. 管理面板（`/config → 照片墙`）

一份文件管完：`config/gallery.json`。

| 能力 | 说明 |
|---|---|
| 批量上传 | 多选本地图片 → 浏览器里压成 WebP（长边 2000、目标 ~300KB）→ **直传图床 `gallery/`**，仓库里只留 URL |
| 从图床选 | 复用站内媒体库弹窗，挑已经传过的图，一个字节都不重新上传 |
| 新照片标签 | 工具栏里一排可勾的胶囊（照片上已有的标签 ∪ 新建的），勾好之后**上传 / 从图床选进来的照片直接带上这些标签**。勾选只存本机 `localStorage`（`melodyxz-galg-upload-tags`），不进仓库；`+新建标签` 回车即建并勾上 |
| 排序 | 拖缩略图到**另一张卡片**上（原生 HTML5 拖放），顺序 = 照片海流动顺序 |
| 拖拽打标 | 拖缩略图到**右侧标签篮的某个标签**上 = 给这张照片加上那个标签（原标签保留）。拖的那张如果已被勾选，则**勾选的几张一起加**；拖到「全部」不做任何事 |
| 标签篮 | 右侧常驻，一行一个标签（带张数）。点名字 = 网格**只看**这个标签（再点取消）；拖动时整条篮子亮起来当落点 |
| 展示分类（眼睛） | 每行右边那颗眼睛 = 该标签在**相册页左侧抽屉**里列不列（写 `railTags`；全开 = 空数组 = 全部）。藏起来的标签只是不出现在抽屉里，照片照样在「全部」里、`?tag=` 也照样能筛。藏过之后篮子底部出现「相册左侧栏：显示全部分类」一键复位 |
| 标签管理（⋯） | 每行最右边「⋯」→ 重命名 / 合并到… / 删除标签。三件事都是**一次改掉所有照片上的标签名**，并同步 `railTags`、本机「新照片标签」勾选和当前筛选；重命名撞上已有标签、或合并目标不存在时都有提示（目标不存在 = 等价于改名）。用 `window.prompt` / `confirm` 确认，提交后才落盘 |
| 标签 | 单张：卡片里回车即加、点标签即删；批量：选中后「加标签 / 去标签」 |
| 删除 | 单张或批量。**只从 JSON 摘掉**，图床上的文件在提交成功之后才清（`state.trash` → `deleteMedia`） |
| 排版参数 | 5 个滑块实时改，同样要保存才写进仓库（只留不会破坏排版的项，见 §3.2） |
| 保存 | 一次 GitHub commit（`commitFiles`），约 1 分钟后生效 |

布局：照片墙这一栏单独放宽到 74rem（`config.css` 里用 `.cfg-main:has([data-config-panel='gallery']:not([hidden]))` 实现，切到别的栏自动收回 880px），
里面是「左网格 + 右标签篮」两栏；≤1023px 折成一栏，标签篮变成网格上方的横排胶囊（触屏没有原生 HTML5 拖拽，此时它只当筛选器用）。

细节：

- 拖放的两种落点靠**目标元素**区分，不额外发明手势：卡片上 = 改顺序，标签篮的标签行上 = 打标。
  `dragover` 在标签篮上必须 `preventDefault`（否则浏览器判定「不许放」，`drop` 不会触发）
- 筛选时被筛掉的卡片只是 `hidden`、**不从 DOM 里摘掉** —— `commitOrder()` 靠 DOM 顺序还原数组顺序；
  「全选」在筛选生效时只覆盖看得见的那些
- 拖拽残留（`is-dragging` / `is-over`）由 `drop` 和 document 级 `dragend` 双保险清理
- id 重复会被自动换成新 id（重复 id 会让筛选/放大认错人）
- 未授权时面板不加载数据（与 `/write`、`/config` 共用同一份写作令牌）

## 9. 移动端与降级

| 场景 | 行为 |
|---|---|
| 桌面（`min-width:900px` 且 `pointer:fine`） | 相机模式：整屏舞台 + 幕布 + 二维拖拽 |
| 手机 / 触屏 / 窄屏 | 滚动模式：**不接管页面滚动**（手指拖拽和滚动、侧滑返回冲突太狠），Banner 就是全站普通首图（不再占满一屏），照片海在它下面留 1rem 缝、按屏宽分 2 列，靠页面自己滚；放大时**占满屏宽**（正好是 2 整列，不会有边界列空档）、保持比例档，并滚到视口上方 16% 处；分类栏默认收起；右下角那颗按钮只剩「退出放大」（没放大时不显示） |
| 禁用 JS | `<noscript>` 里的样式把它变成普通三列瀑布 |
| 排版引擎抛异常 | `new Wall()` 抛错时给根节点加 `gal--fallback`，同样是三列瀑布 |
| `prefers-reduced-motion` | 过渡压到 1ms，星尘不闪不跑 |
| 灯箱里的双指 | 相机模式**只在桌面**开，但灯箱在手机上也一样能双指缩放 / 平移：`Map<pointerId, 坐标>` 记账，第二根手指按下就切手势；`.gal-lb__canvas` 是 `touch-action: none`，所以浏览器不会自己去做页面缩放 |

### 灯箱双指缩放的算法

```
缩放  z1 = clamp(z0 × (当前两指间距 / 按下时的间距), 1, 6)
锚点  两指中点：按下时中点下面那个像素，全程黏在手指中间
平移  pan1 = mid_now − (mid_start − pan0) × (z1 / z0)
```

`mid_*` 都换算成「相对画布中心的偏移」，所以和滚轮那条
「`pan = c − (c − pan) × ratio`」是同一个公式，只是锚点从光标换成了两指中点。
间距不变、中点移动 = 纯平移；一路捏回 1× 时 `pan` 直接归零（不留半像素偏移）。

几个必须处理的边角：

| 情况 | 处理 |
|---|---|
| 松手后手机补发 `click` | `lbIgnoreClickUntil`（缩放/拖动结束后 220–400ms 内不把这次 click 当「点空白关闭」），否则一松手灯箱就关 |
| 双指松开一根、还按着一根 | 用剩下那根重新基准 `lbDrag`（`px/py` 取当前 `pan`），接着拖不会跳 |
| 按了第三根手指 | 不进基准、不算间距，等它松开 |
| 换照片 / 关灯箱 | `lbTouches.clear()` + `lbPinch = null` + 摘掉 `is-dragging` / `is-pinching`，下次打开不带旧手势 |

### 滚动模式里两个「横向溢出」的坑

手机上照片墙是普通文档流，任何一点点超出屏幕宽度的东西都会变成**整页的横向滚动条**，
表现是「整站像被推歪了、导航胶囊看着要出屏幕」。踩过两次：

| 病根 | 症状 | 治 |
|---|---|---|
| `.gal-hint` 基础样式是 `position: fixed` + `left: 50%` + `translateX(-50%)`；滚动模式只把它改成 `relative` 就以为居中了，`left: 50%` 还在 → 整块被往右推半屏（实测 `scrollWidth` 424 > 375） | 页面多出一条横向滚动条，提示条跑到屏幕外 | 滚动模式里把 `left / right / top / bottom` 一起还原成 `auto`，居中交给 `margin: auto` |
| 首屏排版的那一刻页面还没有滚动条 → `view.clientWidth` 比真实可用宽度多 15px；排完版照片海把页面撑长、滚动条冒出来，右边那列就悬在屏幕外 | 同样是一条横向滚动条，右边一列被切掉 15px | ① `html.gal-page:not(.gal-camera) { overflow-y: scroll }` 先把槽位占住；② `watchWidth()` 用 `ResizeObserver` 盯着 `.gal-view` 的宽度，宽度真变了（`window.resize` 不会来）就 `layout({ instant: true })` 重排 |

两条都要留着：第一条防「一开始就错」，第二条兜「后来才变」（滚动条消失、字体加载、
横竖屏切换后的布局都要靠它自愈）。

## 10. 已知取舍 / 还能做什么

- **缩略图被裁成规整比例**：一律吸附到九档菜单（9:16 … 3:1），不在这九档里的原比例会被裁掉一点。
  换来「高度全是整数、格点对齐残差恒为 0」；想看原图点第二次进灯箱（灯箱永远是原比例）。
- **放大照不再是原比例**：它是「该图吸附后那一档的放大版」。2:1 / 3:1 的全景放大时按 16:9 取景
  （照原比例放大只是一条看不清的扁横条）。
- **放大照一定装得进一屏，但矮窗口下会被裁矮一点**：宽度必须占整列（否则两侧留空档），
  高度就被「宽 ÷ 比例」定死了。所以选 k 时**先满足高度装得下**（1440×900 下 9:16 是 2 列 440×782，
  可用高 814，装得下）；窗口矮到 2 列竖图都装不下时（1440×780 / 1280×720 实测），
  把盒子裁到可用区高度（782 → 694 / 634），照片上看不到最上最下那一点，点第二次进灯箱看全图。
  这是「不许有缺口」「整列铺满」「不出屏幕」三条硬约束下唯一的做法 ——
  不裁就只剩「退回 1 列 = 和缩略图一样大 = 点了没反应」。
- **整体大小只有一个旋钮：`columnWidth`**。照片、列数、放大照宽度全部由它派生；
  缺省 216（1440 屏一屏 6.4 列），想更大改 288（4.9 列）、更小改 144（9.9 列）。
  改它不需要动排版、动画、任何一条不变量。
- **点开时会有十来张照片动一下**：被放大照压到的那些必须让开，而整片海里唯一空着的地方
  就是板子下沿那一排 —— 所以它们往那儿走（位移中位数 120–640px，少数要跨一屏）。
  三件事让它不扎眼：① 十几列**完全静止**（连 `transform` 都不写）；
  ② 走远的那几张（>1100px）单独走 220ms + 140ms 延迟的「快速退场」，不是慢慢横穿画面；
  ③ 其余只是最后一排的高度变一点点（在屏幕外）。
  想彻底不动，只能让被压到的照片躺在放大照背后 —— 那是「覆盖」，已明确否决。
  实测（列宽 216）：**平均 14.4 张移动、6 张走远**（列宽 288 时 29 张 / 9 张，改造前 155 张全动）。
  把整体调小之后「要让开的人」也跟着变少 —— 这是缩小尺寸的附带好处。
- **每列末格 + 带上沿那一格会破例**：为了三条边（放大照上沿 / 下沿 / 板底线）都对齐，
  这两格允许不是菜单高度（末格最低 `MIN_LAST=96`、最高 2.5 倍；
  带上沿那格最长拉到 2.5 倍、最短裁到约 55%）。`object-fit: cover` 只换取景框，照片不变形。
- **板底会整体下移**：放大照把某列撑得比原来长时，底线是一条新的直线（位置变了，但依然是一条直线）。
- **贴边照片不再是「正正中中」**：程序化居中允许镜头越出画布边框（`camBounds(true)`，越出去的那片是星尘），
  所以贴边的照片也能真居中（实测横纵偏差 ≤ 1px）；松手 / 复位之后镜头会回到画布范围内。
  以前用 `camBounds(false)` 只允许露出 6%，贴顶的那一排就永远「贴着导航下沿、不居中」。
- **照片特别少的时候（7~8 张）**：整片海比放大照还矮，那点高度只能长出去 ——
  属于「没料可用」而不是排版出错。
- **没虚拟化**：几百张以内 `loading="lazy"` 足够。
- **管理面板排序没有移动端方案**：原生 HTML5 拖放在触屏上不生效，但管理只在桌面用。
- **灯箱没有图片预加载**：← → 切图时即取即显（图床有 CDN 缓存，通常够快）。

### 怎么验收（改排版之后必跑）

`checkInvariants()` 只在 `import.meta.env.DEV` 下跑，每次排版都把结果写进
`[data-gal-grid]` 的 `data-gal-check`（`ok` 或无空格的一串 `重叠/空洞/越界/底线` 罪名）。
逐张扫一遍就能代替肉眼：

```js
// Playwright：browser_run_code_unsafe，一次 80 张（MCP 单次调用 ~30s 上限）
for (const id of ids.slice(0, 80)) {
  await page.evaluate((id) => document.querySelector(`[data-gal-cell][data-id="${id}"]`)?.click(), id);
  await page.waitForTimeout(55);
  const chk = await page.evaluate(() => document.querySelector('[data-gal-grid]').dataset.galCheck);
  if (chk !== 'ok') fails.push({ id, chk });
  await page.keyboard.press('Escape');
  await page.waitForTimeout(35);
}
```

> `data-gal-focus` 里的 `band=top..bottom k=N col=M` 是放大照的真实占位矩形，
> 自己写校验脚本时用它判断「哪些列被放大照占着」。
> 放大照和上一张之间隔的是 `band.top − gap`、和下一张之间是 `band.bottom + gap`，
> 这两处是合法布局，不是空洞；列的首格从 y = 0 起（放大照顶在列首时才是 `band.bottom + gap`）。
> `data-gal-check` 现在还多查三条：**放大照必须铺满它那 k 列**（`bandLeft` / `bandRight`）、
> **带上沿上方那张必须正好停在「上沿 − gap」**（`bandTopEnd` / `bandTop`）、
> **带下沿下方那张必须正好接在「下沿 + gap」**（`bandBottom0` / `bandBottom`）。
> 这三条是「放大照四周只剩一个标准间隙」的兜底断言 ——
> 曾经因为「带附近留白一律算合法」，把 100~170px 的空档漏了过去，而且它**随窗口尺寸变化**，
> 只在某些尺寸下看得见。改排版时务必在多档视口下各扫一遍。
>
> 除了 160 张演示数据，还要**换一批随机比例**再跑一遍（含 1:3 长截图、3:1 全景、极端比例）：
> 极端比例走的是「夹到边界档 / 全景按 16:9 取景」这两条分支，演示数据里的比例都是规整档，覆盖不到。
